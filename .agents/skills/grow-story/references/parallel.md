# 并行探索与串行提交

有工具且预计有收益时使用，不固定工作者数量；资源不足时串行运行并如实说明。该规范指导执行，不代表已实现无人值守调度器。

1. 协调者固定同一基线快照及版本、SHA256。给每个探索实例只读基线、必要原文和技能，在各自候选目录工作。不要给预期赢家；允许自主不同方向。工作者不得修改正式状态或正式记忆，也不得自行提交。
2. 工作者仅返回局部变更包、简短方案与审核依据。临时候选的渲染结果可由程序生成，不要求模型重写完整状态。用稳定编号且保持各候选隔离；编号碰撞不靠简单拼接解决。
3. 需要时让人物、世界事实、跨剧情联系等审核并行读取同一冻结候选及原文，只返回证据和意见。修改候选后，受影响的旧审核失效，复核后再采用；多票一致不保证正确。
4. 协调者在相近探索机会下统一选择。可保留原版、一个候选或经重新审查的组合；即使操作目标不同，也检查共享人物、时间、世界条件和因果，不能认为文件不冲突就语义独立。拟组合时先基于同一基线形成一个新包并整体复核。
5. 只有一个提交者使用 apply_patch.py 预检并提交采用包，连同对应记忆一次发布。脚本的锁、版本和散列拦截过期提交。若正式状态已改变，重新读取新基线、重新协调和审核后构造新包；禁止仅改版本号或散列强行提交旧内容。
6. 下一轮在上一轮提交完成后读取新快照。保留候选与采用结果、审核覆盖、失败及重试记录；报告实际运行的实例和阶段，结束明确说明，不暗示无人值守后台继续运行。

程序并发测试只证明相同基线两个包不能都直接覆盖当前状态，不证明并行创意质量、自动选择或语义审核稳定性。
